# v0.1 구현·검증 기록 — 2026-09-29

## 요청과 결과

사용자 요청(DM1402 및 후속): 지갑을 생성하는 프로그램과 그 지갑으로 주문을 실행하는 자동매매 기능을 구현한다.
수익 목표 최적화는 아직 우선순위가 아니다.

**암호화 지갑, 공식 SDK 주문 어댑터, 매매 루프를 구현했다. 실제 BTC 공개 시세로 모의 진입·청산까지 실행했다.**
새 테스트 지갑의 테스트넷 담보는 0이므로 거래소 주문 전송·승인·체결·취소 성공은 아직 검증하지 못했다.
실제 자금을 입금하거나 메인넷 주문·송금을 실행하지 않았다.

## 구현 범위

- Python CLI: `wallet create/check`, `quote`, `account`, `order-status`, `order`, `cancel`, `reconcile`, `bot`.
- `eth-account`의 난수 키 생성, scrypt 기반 암호화 V3 keystore, 로컬 메시지 서명/주소 복구 확인.
- 지갑·암호 파일 0600, 저장 폴더 0700. 기존 파일 덮어쓰기와 비밀 파일의 심볼릭 링크를 거부한다.
- Hyperliquid 공식 Python SDK의 주문/취소 서명 및 전송 코드. BTC 자산 ID와 수량 정밀도는 네트워크별로 조회한다.
- 닫힌 1분봉 이동평균 신호, 중복 방향 진입 방지, 반전 시 reduce-only 청산 후 확인, 신규 명목금액·주문 수 제한.
- 오래된 호가/불연속 캔들 거부, 평가손실 감지 시 포지션 청산 시도, 로컬 계좌별 실행 잠금.
- 요청 전 영속 journal 기록. 불확실한 응답은 자동 재전송하지 않고 계좌/주문 상태 조회로 확인한다.
- 기본 `paper`, 테스트넷, 운영자가 직접 활성화하는 메인넷 실행 경로를 분리했다.
- 개인키 없이 시세/계좌 조회 가능. paper는 지갑을 열거나 거래소 서명 주문을 전송하지 않는다.

수익금 출금/자동 송금, API wallet 승인, 자동 입금, 상시 서비스/예약 작업은 포함하거나 실행하지 않았다.

### 자동 검사 내용

- 암호화 파일에 평문 키/암호가 남지 않는지, 실제 서명 검증, 잘못된 암호/지갑 용도, 파일 권한/덮어쓰기 거부.
- 롱/숏 왕복 손익과 bid/ask 스프레드·추가 슬리피지·수수료의 독립 계산 비교.
- 주문 예산 도달 후에도 청산 허용, 같은 신호 반복 진입 방지, 유효하지 않은 숫자/오래된 호가 차단.
- SDK 주문/취소 서명과 테스트넷 BTC 자산 ID 확인, IOC 진입과 reduce-only 청산 경로.
- 담보/명목금액/호가 단위/수량 정밀도/미체결 주문 검사, 메인넷 기본 차단, 로컬 동시 실행 잠금.
- 타임아웃·불명확한 성공 응답 이후 재시작해도 미해결 journal 유지. 조회 결과가 불확실하면 재전송하지 않음.
- CLI paper 루프가 거래소 주문 어댑터를 생성하지 않는지, 평가손실 중단 신호가 일반 신호에 우선하는지 확인.

### 테스트 지갑과 자금 조건

새 지갑과 테스트용 암호 파일은 저장소 밖의 소유자 전용 폴더에 저장했다. 개인키·암호·keystore 내용은 이 기록에 포함하지 않는다.
둘 다 같은 서버에 있으므로 이는 테스트 환경일 뿐 실제 자금 보관의 보안성을 입증하지 않는다.
`testnet` 표시는 프로그램의 용도 검사이며 EVM 주소 자체를 메인넷에서 쓸 수 없게 만드는 장치가 아니다.
테스트용 주소에 실제 자금을 보낼 것을 요청하지 않았다.

새 계좌는 테스트넷 담보가 없어 주문 전송 전에 차단됐다. 검사 중 HTTP 요청은 `/info`만 허용하도록 계측했다.
공식 Faucet는 같은 주소의 메인넷 입금 이력을 요구하므로 새 지갑 생성만으로 무료 테스트 토큰 수령이 보장되지 않는다.
이번 확인 문서에는 최소 입금액이 명시되어 있지 않다. [공식 Faucet 조건](https://hyperliquid.gitbook.io/hyperliquid-docs/onboarding/testnet-faucet)

## 아직 검증하지 않은 사항

- 테스트넷 거래소의 인증/서명 승인, 실제 주문 체결/부분 체결/취소, 거래소 장애 복구.
- 메인넷 실거래 및 모든 계좌/마진 모드. 공개 접근 성공은 인증 거래 가능성의 증거가 아니다.
- 수익성, 펀딩·청산·호가 깊이/시장 충격을 반영한 성능, 장기 연속 운영.
- 별도 서버/기기와의 동시 주문 제어, 상시 거래소 손절 주문, 강제 종료 시 포지션 자동 정리.

평가손실 감지값은 최대 손실 보장이 아니다. 오류·응답 불확실성·강제 종료 때 새 청산 주문을 자동 전송하지 않으므로 포지션이 남을 수 있다.
정상 종료의 테스트넷 청산은 `--flatten-on-exit`을 명시해야 한다. paper는 정상 종료 시 모의 포지션을 닫는다.

다음 외부 검증 단계는 **테스트 자금이 있는 계좌에서 제한된 테스트넷 주문 → 상태 확인 → 취소/청산 확인**이다.
사용법과 장애 시 처리 절차는 [운영 가이드](OPERATOR_GUIDE.md)에 있다.
